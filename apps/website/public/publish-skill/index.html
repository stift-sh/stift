Publish a skill.

A skill your org keeps in stift can be shared with everyone. Every stift server is a registry: an admin publishes an org skill as @org/name, and anyone installs it with one command, no account and no login, every file verified against the published manifest.

Pick a slug

the @org half of every reference, chosen once

Published skills are addressed as @<slug>/<name>. The slug is your org's: 2–39 lowercase letters, digits or hyphens. Set it on the org card in the web app (Members), with STIFT_ORG_SLUG when you start the server, or over the API.

sh
# self-host: applied while the org still has the default slug
$ STIFT_ORG_SLUG=acme docker compose up -d

The slug is locked once anything is published: renaming it would break every reference anyone has installed. Pick the name people should type.

Publish

admins, from the terminal or the skill's page

Anything you can publish is already an org skill (see Share skills in your company): a skills/<name> unit in the org scope with a SKILL.md. Publishing takes a snapshot of it under a public name and a license.

sh
$ stift skills publish skills/deploy --license MIT
published claude/org/skills/deploy v3 as @acme/deploy v1 (1 files)
# later, after another push of skills/deploy:
$ stift skills publish skills/deploy
published claude/org/skills/deploy v5 as @acme/deploy v2 (1 files)
  • Name. Defaults to the unit's last segment (skills/deploy → deploy); --name changes it on the first publish and it is fixed after that. One public name maps to one org unit.
  • License. An SPDX identifier (MIT, Apache-2.0) or LicenseRef-<name>. Required the first time; a later --license changes it going forward.
  • Version. Head by default; --version N publishes a known-good older version of the unit.
  • In the browser. The skill's page has a Published card with the same form, the install command ready to copy, and every published version.

Install anywhere

one command, no account
sh
$ stift skills install @acme/deploy --registry https://stift.acme.example
installed @acme/deploy v2 → ~/.claude/skills/deploy: 1 written, 0 unchanged
$ stift skills install @acme/deploy@1 --agent cursor   # pin a version, pick the agent
$ stift skills search deploy --registry https://stift.acme.example

The files land as an ordinary directory in the agent's own config, each one checked against the sha256 in the published manifest; a tampered or truncated download fails the install and leaves nothing half-written. Nothing is reported back to the registry.

--registry says which server to ask. Without it the CLI tries STIFT_REGISTRY_URL, then registry in its config file, then the server you are logged in to if it is a registry, then app.stift.sh. Later, stift skills outdated lists registry installs that are behind, and install --upgrade moves them forward, refusing to overwrite your edits unless you pass --force.

Versions and unpublishing

a publish sequence, and a snapshot nothing can change

Public versions count 1, 2, 3… on their own, independent of the org unit's history; each records the source version it was copied from. Publishing copies the manifest, so editing, rolling back or even deleting the org unit never changes what people installed. Publishing identical files again is refused.

sh
$ stift skills unpublish @acme/deploy@2    # or the whole skill: @acme/deploy
unpublished deploy v2: hidden from search and latest, still resolves by number
$ stift skills restore @acme/deploy@2

Unpublishing hides a version, or the whole skill, from search and from latest. It still resolves by number, so existing installs keep verifying and stift skills outdated tells their owners it was unpublished rather than offering an upgrade.

What a registry is

four read-only routes, no token
sh
$ curl https://stift.acme.example/v1/registry/skills/@acme/deploy      # latest visible version
$ curl https://stift.acme.example/v1/registry/skills/@acme/deploy/2    # a numbered version, immutable
$ curl https://stift.acme.example/v1/registry/skills?q=deploy          # search

A published version is its manifest plus its files, served by digest and only for digests that manifest lists. The org's other files stay behind the token. Numbered versions and their files are immutable and cached as such; latest and search are cached for a minute. Rate limiting is your reverse proxy's job.

Keep it private

nothing is public until an admin publishes

A server exposes nothing through the registry until an admin publishes a skill. Companies that want the guarantee set STIFT_REGISTRY=off: the registry routes disappear and publishing is refused, while the org scope keeps working as the team's own registry.
