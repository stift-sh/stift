Share skills in your company.

The skills, subagents and commands that make an agent useful in your codebase usually live on one person's laptop. With a stift server, admins publish them once, everyone's agent picks them up, every change is a version you can diff and roll back, and you can see who is running what.

Start a server

one container, a Postgres database and a bucket

Skip this step on Stift Cloud. To self-host, the compose file brings everything it needs; for your own database and bucket see Self-host a server.

sh
$ curl -fsSLO https://raw.githubusercontent.com/stift-sh/stift/main/docker-compose.yml
$ docker compose up -d
$ docker compose logs server   # the first-boot admin token, shown once

A server is one org (name it with STIFT_ORG_NAME in the compose file). The token from the log belongs to its first admin; log in with it and you are ready to add everyone else.

sh
$ curl -fsSL https://stift.sh/install.sh | sh
$ stift login https://stift.acme.dev --token stf_...

Add your people

users have a role, tokens belong to users
sh
# creates the user and prints a ready-made login line with a first token, once
$ stift user add --email alice@acme.dev alice
$ stift user add --admin bob

$ stift user list
$ stift user role alice admin
$ stift user rm alice            # revokes her tokens too

The same is in the web app under Members. A member makes further tokens for their other machines themselves (stift token create desktop); an admin can mint one for somebody else with --user, which is how CI gets a token.

Publish to the org

admins write the org scope, from the terminal or the browser

Org units live in ~/.stift/org/<agent>/ on the machine that publishes them, laid out like the agent's own directory.

sh
$ mkdir -p ~/.stift/org/claude/skills/deploy
$ $EDITOR ~/.stift/org/claude/skills/deploy/SKILL.md
$ stift push --skills --scope org
pushed     claude/org/skills/deploy  v1 (1 files)
  • Every push is a version. stift skills history, diff and rollback work per unit with --scope org; the web app shows the same timeline with rendered markdown and a diff between any two versions.
  • No silent overwrites. A push on top of a version you have not pulled is rejected as stale.
  • Edit in the browser. Admins can create and edit org skills in the web app; members see them read-only.
  • Never synced: settings*.json, .mcp.json, env files and dotfiles, because they hold secrets and run code.
  • Share it beyond the org. Publish an org skill as @org/name for anyone to install: Publish a skill.

Pull on every machine

a subscription: the org's newest version, linked into the agent
sh
$ stift pull --skills --scope org
pulled     claude/org/skills/deploy  v1: 1 written, 0 deleted, 0 unchanged

Org units are mirrored into ~/.stift/org/ and each one is symlinked into the agent's directory (~/.claude/skills/deploy), so they never collide with personal skills, and a unit removed from the org disappears with its link. The background service that stift login starts keeps the mirror current, so nobody has to remember to pull.

Each pull is reported back. The skill's page in the web app lists Pulls: which user has which version on which host, so "is everyone on the new deploy checklist yet" has an answer.

Fork a skill

a detached copy that remembers where it came from

A subscription is read-only by design. To adapt an org skill, install it: that copies it into your own agent directory as ordinary files and records the version it was copied from.

sh
$ stift skills install skills/deploy --replace   # --replace: swap the subscription for a copy
$ stift skills outdated
AGENT    NAME                         INSTALLED ORG       STATUS
claude   skills/deploy                v1        v3        behind
$ stift skills install skills/deploy --upgrade   # --force to overwrite your edits

Roles

two of them; everyone can read everything in the org
memberadmin
read sessions, skills, membersyesyes
write project scope and own user scopeyesyes
write org scopenoyes
delete sessionstheir ownany
manage tokenstheir ownthe org's
add and remove users, change rolesnoyes

A token carries the role of its user, so a role change applies to every machine at once. The server refuses to demote or remove the last admin.

Limits

unlimited when you self-host, unless you say otherwise
VariableCaps
STIFT_MAX_SKILLSunits (skills, agents, commands, CLAUDE.md) across all scopes
STIFT_MAX_STORAGE_BYTESbytes of unit file content
STIFT_MAX_SEATSusers in the org

Set a positive integer, or unlimited to clear a limit. A write over a limit is refused with 402 and a message naming it; lowering a limit never deletes anything. The org card in the web app and GET /v1/org show limits next to usage. On Stift Cloud the same columns are set by your plan, which is the only difference.
